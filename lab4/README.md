# Задание 4: аутентификация и авторизация

REST API приюта для животных. Приложение ведёт животных, вольеры, учётные записи, заявки
на усыновление и акты передачи животного семье. Данные хранятся в PostgreSQL, доступ —
через Spring Data JPA. Доступ к API закрыт HTTP Basic, изменяющие запросы защищены
CSRF-токеном.

## Сущности и связи

| Сущность              | Ресурс                         | Атрибуты                                                         |
| --------------------- | ------------------------------ | ---------------------------------------------------------------- |
| Пользователь          | `/api/users`                   | логин, имя, адрес электронной почты, хеш пароля, роль, состояние |
| Вольер                | `/api/enclosures`              | название, допустимые виды животных, вместимость                  |
| Животное              | `/api/animals`                 | кличка, вид, возраст, статус размещения, вольер                  |
| Заявка на усыновление | `/api/adoption-applications`   | животное, заявитель, мотивация, статус, дата подачи              |
| Акт передачи          | `/api/animal-handover-records` | заявка, дата подготовки, дата подтверждения, статус              |

Связи:

- пользователь 1—N заявок в роли заявителя;
- животное 1—N заявок;
- вольер 1—N животных, животное может быть не размещено;
- заявка 1—1 акт передачи;
- вольер 1—N допустимых видов, хранятся в `enclosure_species`.

Статусы:

- животное: `AVAILABLE` — в приюте и доступно, `RESERVED` — есть активная заявка,
  `HANDED_OVER` — передано семье;
- заявка: `PENDING`, `APPROVED`, `REJECTED`, `CANCELLED`;
- акт передачи: `PREPARED`, `CONFIRMED`, `RETURNED`;
- пользователь: роль `ADOPTER` или `STAFF`, состояние `ACTIVE` или `BLOCKED`.

## Аутентификация

Учётные записи хранятся в таблице `users`, пароли — в виде BCrypt-хешей.

| Запрос                    | Назначение                                              |
| ------------------------- | ------------------------------------------------------- |
| `GET /api/auth/csrf`      | выдать CSRF-токен, доступен без аутентификации          |
| `POST /api/auth/register` | зарегистрировать заявителя, доступен без аутентификации |
| `GET /api/auth/me`        | показать текущую учётную запись                         |

Все остальные запросы требуют HTTP Basic. Регистрация всегда создаёт учётную запись
в роли `ADOPTER` и в состоянии `ACTIVE`: роль и состояние задаёт сервер, поэтому
повышенные привилегии получить нельзя. Пароль должен содержать буквы и цифры и быть
не короче 10 символов; логин и адрес почты должны быть уникальны.

Заблокированная учётная запись не проходит аутентификацию и получает 401 — так же,
как при неверном пароле.

## CSRF-защита

Токен выдаётся запросом `GET /api/auth/csrf`: значение приходит в теле ответа и в
cookie `XSRF-TOKEN`. Изменяющие запросы (`POST`, `PATCH`, `DELETE`) должны передавать
его в заголовке `X-XSRF-TOKEN`. Cookie нужно сохранять между запросами.

## Роли и права

| Действие                                                           | ADOPTER | STAFF        |
| ------------------------------------------------------------------ | ------- | ------------ |
| Просмотр животных и вольеров                                       | да      | да           |
| Создание, изменение, удаление животных и вольеров                  | нет     | да           |
| Размещение животного в вольере                                     | нет     | да           |
| Просмотр списка пользователей, создание и удаление учётных записей | нет     | да           |
| Просмотр и изменение своего профиля                                | да      | да           |
| Блокировка учётной записи                                          | нет     | да           |
| Подача заявки                                                      | да      | да           |
| Просмотр, изменение и отзыв своей заявки                           | да      | только своей |
| Просмотр чужих заявок, списка заявок                               | нет     | да           |
| Одобрение и отклонение заявок                                      | нет     | да           |
| Подготовка, подтверждение и возврат передачи                       | нет     | да           |

Права проверяются аннотациями `@PreAuthorize` на контроллерах. Часть правил зависит
от контекста: заявку может изменить и отозвать только её автор, профиль — только сам
пользователь или сотрудник.

## Ограничения целостности

| Ограничение                                                                                     | Где выражено                                                   |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| заявка ссылается на существующих животное и пользователя, акт — на заявку, животное — на вольер | внешние ключи                                                  |
| удаление вольера с животными, животного или пользователя с заявками, заявки с актом отклоняется | сервисный слой, ответ 409                                      |
| логин и адрес почты уникальны                                                                   | `UNIQUE`                                                       |
| одна заявка на пару «животное — заявитель»                                                      | `UNIQUE (animal_id, applicant_id)`                             |
| один акт на заявку                                                                              | `UNIQUE (application_id)`                                      |
| возраст неотрицателен, вместимость положительна                                                 | `CHECK`                                                        |
| допустимы только известные статусы и роли                                                       | `CHECK`                                                        |
| дата подтверждения заполнена только у `CONFIRMED` и `RETURNED`                                  | `CHECK`                                                        |
| вместимость вольера не превышается                                                              | сервисный слой, строка вольера блокируется на время транзакции |
| смена списка видов вольера не оставляет в нём животных другого вида                             | сервисный слой                                                 |

Схема и тестовые записи — в `db/init.sql`.

## Бизнес-операции

| Операция             | Запрос                                            | Затрагиваемые сущности                 | Условия выполнения                                                                                   |
| -------------------- | ------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Размещение в вольере | `POST /api/animals/{id}/placement`                | животное, вольер                       | животное не передано семье, вид разрешён вольером, есть свободное место                              |
| Одобрение заявки     | `POST /api/adoption-applications/{id}/approval`   | заявка, животное, конкурирующие заявки | заявка в статусе `PENDING`, животное не передано семье; остальные заявки на это животное отклоняются |
| Отклонение заявки    | `POST /api/adoption-applications/{id}/rejection`  | заявка, животное                       | заявка в статусе `PENDING`; если активных заявок не осталось, животное освобождается                 |
| Отзыв заявки         | `POST /api/adoption-applications/{id}/withdrawal` | заявка, животное                       | отзывает сам заявитель, статус `PENDING` или `APPROVED`, акт передачи не оформлен                    |
| Возврат в приют      | `POST /api/animal-handover-records/{id}/return`   | акт, заявка, животное                  | акт в статусе `CONFIRMED`; акт переходит в `RETURNED`, заявка отменяется, животное снова доступно    |

Подтверждение передачи — `PATCH /api/animal-handover-records/{id}` со статусом
`CONFIRMED`: животное получает `HANDED_OVER` и покидает вольер.

Статусы меняются только этими операциями. `PATCH` животного правит кличку, вид и
возраст, `PATCH` заявки — мотивацию, пока заявка в статусе `PENDING`.

## Ошибки

| Код | Причина                                                                  |
| --- | ------------------------------------------------------------------------ |
| 400 | тело запроса не прошло проверку                                          |
| 401 | нет учётных данных, неверный пароль или заблокированная запись           |
| 403 | роль или контекст операции не разрешают действие, отсутствует CSRF-токен |
| 404 | ресурс не найден                                                         |
| 409 | операция нарушает состояние данных                                       |

Ответы 401 и 403 возвращаются в том же формате, что и остальные ошибки, без деталей
аутентификации.

## База данных

Нужен PostgreSQL 15 или новее.

```bash
psql -U postgres -f db/init.sql
```

Скрипт пересоздаёт базу `shelter` и роль `shelter_app`, создаёт таблицы, ограничения и
тестовые записи. Роль не является суперпользователем и не может создавать объекты: ей
выданы `CONNECT`, `USAGE` на схему `public`, `SELECT`, `INSERT`, `UPDATE`, `DELETE` на
таблицы и `USAGE`, `SELECT` на последовательности.

Параметры подключения задаются переменными окружения:

```bash
cp .env.example .env
```

| Переменная    | Назначение         |
| ------------- | ------------------ |
| `DB_URL`      | строка подключения |
| `DB_USERNAME` | пользователь базы  |
| `DB_PASSWORD` | пароль             |

Файл `.env` в репозиторий не попадает. Пароль в `db/init.sql` демонстрационный: при
развёртывании замените его и значение `DB_PASSWORD`.

## Коллекция запросов

`postman_collection.json` повторяет сценарий работы приложения: получение CSRF-токена,
регистрация, проверка отказов без аутентификации и для заблокированной записи, работа
с учётными записями, животными, заявками и актами от имени заявителя и сотрудника,
выполнение бизнес-операций, проверка недостатка полномочий, CSRF и бизнес-ограничений,
удаление созданных записей.

Запросы выполняются по порядку, CSRF-токен и идентификаторы созданных объектов
сохраняются в переменные коллекции, cookie `XSRF-TOKEN` должен сохраняться между
запросами. Перед прогоном база пересоздаётся через `db/init.sql`.

## Слои

| Слой       | Содержимое и ответственность                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------- |
| api        | контроллеры, DTO, проверка тела запроса аннотациями                                                              |
| security   | `SecurityFilterChain`, HTTP Basic, CSRF, загрузка учётных записей                                                |
| service    | бизнес-логика и бизнес-операции, переходы статусов, проверка состояния связанных объектов                        |
| repository | запросы к базе через Spring Data JPA                                                                             |
| domain     | сущности, роли и статусы                                                                                         |
| exception  | `NotFoundException`, `ConflictException` и `ApiExceptionHandler`, приводящий исключения к единому формату ответа |
